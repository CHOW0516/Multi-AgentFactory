# P3 integration requests

## P1 foundation

- Consider a dedicated transactional outbox and a caller-supplied message ID for `publish_task` and `publish_event`. P3 stages events in `audit_log` and recovers published task IDs from `agent_messages`. The consumer still uses at-least-once delivery. These interfaces would let it repeat a publish with the same message ID after an ambiguous broker response.
- The P3 router registers the desktop's `/ws` URL during FastAPI startup, in addition to the route discovered at `/api/ws`. Integration tests should run the application lifespan to exercise `/ws`.
- Expose a streaming mode on the shared Claude client if the desktop needs token-by-token answers. P3 sends tool progress as plain-text chunks, then sends the final answer in chunks after the shared client returns it.
- **Done (connect-everything):** Emit a terminal simulator count for each finished slot. The current simulator only emits counts before the slot ends and floors the result after applying noise. Until that changes, a full manual count or a `done` slot is needed to move simulated work into QC verification.

## P2 domain agents

- Keep the section H tasks repeatable after broker redelivery and after a workflow timeout, especially holds, lock/release, purchase requests, close, and draft creation. P3 discards stale results, while the agent owns idempotency of the underlying side effect.
- Include the revision's `previous_order_id` and persist the replacement order's document before the revision event. P3 waits for old holds and plan release before starting a known replacement order.
- `order.draft_customer_reply` receives `plan_option_id: null` for a decline. A counter-offer receives the selected later plan option. `order.close_order` is sent only after QC verification succeeds.
- Keep `POST /api/plan/what-if` free of factory state changes. Chat invokes this exact endpoint in process using the caller's permissions and returns an availability error when Planning is absent.

## Desktop integration

- Keep `user_ids` explicit for live notifications. Empty recipient lists send to zero users under section 4. P3 broadcasts general state events through their separate contracted event types.
